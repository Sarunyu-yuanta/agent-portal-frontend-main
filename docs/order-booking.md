# Order booking — การจองคำสั่งซื้อล่วงหน้า

ฟีเจอร์เดียวที่ **เขียนข้อมูล** ในพอร์ทัลนี้ (ที่เหลืออ่านอย่างเดียว) — ยังเป็น mock
ทั้งหมด ไม่มี endpoint ไม่มี `fetch`

เปิด/ปิดที่ `ORDER_BOOKING_ENABLED` ใน [`src/lib/feature-flags.ts`](../src/lib/feature-flags.ts)
ปิดแล้วหน้าสินค้ากลับไปเป็นลิงก์ "สร้างคำสั่งซื้อ" ภายนอกเหมือนเดิม และ `/orders` redirect
ไป `/product-catalog`

## ขอบเขต — แท็บตามสินทรัพย์ สามแบบ

`/orders` แบ่งเป็นแท็บตามสินทรัพย์ (ลำดับเดียวกับ Product Catalog) — ดู
[`orders/order-tabs.ts`](<../src/app/(dashboard)/orders/order-tabs.ts>) แต่ละแท็บเป็นหนึ่งในสามแบบ:

| แบบ | แท็บ | flow |
| --- | --- | --- |
| **basket** | Thai Structured, Global Structured | จองจนครบ basket (notional) → ส่งคำสั่งซื้อครั้งเดียว → สินค้าปิด |
| **quota** | Fixed Income, Global Bond | แต่ละรายการจองส่งคำสั่งซื้อได้ทันทีเมื่อวงเงินผ่าน ไม่ต้องรอครบ → สินค้าปิดเมื่อใช้โควตาครบ |
| **transactions** | Stock, TFEX, Mutual Fund | ไม่มีการจอง — แสดงรายการซื้อขายของลูกค้าผ่านแพลตฟอร์มต่าง ๆ (อ่านอย่างเดียว) |

ค่าเริ่มต้นของ `/orders` คือแท็บ Stock (`?tab=` ว่าง)

### โต๊ะที่จองได้

| โต๊ะ | แบบ | หน้าสินค้า | id ของ book |
| --- | --- | --- | --- |
| **Global Structured** | basket | `/product-catalog/product/:id` | id ของสินค้าตรง ๆ (`ko-wmt`) |
| **Thai Structured** | basket | `/product-catalog/thai-structured/:theme` | `thai-` + theme (`thai-chips`) |
| **Fixed Income** | quota | `/product-catalog/fixed-income/bond/:id` | `fi-` + bond id (`fi-mqdc482b-0`) — จองได้เฉพาะหุ้นกู้ที่ `action: "invest"` |
| **Global Bond** | quota | `/product-catalog/global-bond/:issuer` | `gb-` + bond row ของ issuer (`gb-m1`) |

เพิ่มโต๊ะทีหลัง = แก้ [`orders/bookable-products.ts`](<../src/app/(dashboard)/orders/bookable-products.ts>)
(id prefix, `findBookableProduct`, `bookingModeFor`) + ติดปุ่มที่หน้าสินค้าของโต๊ะนั้น +
เพิ่มแท็บใน `order-tabs.ts`

`/orders/:id` เป็น namespace เดียวของทุกโต๊ะ — prefix `thai-` / `fi-` / `gb-` คือสิ่งที่
`findBookableProduct()` ใช้แยกทาง ไม่ใช่แค่ความสวยงาม

### แบบ quota (หุ้นกู้)

- **โควตาเป็น mock** — ยังไม่มีในข้อมูล catalogue เลือกจากบันไดค่าคงที่ตาม id
  (`fixedIncomeQuotaThb`, `globalBondQuotaUsd`) ต่อ backend แล้วให้มาจากสินค้า
- `OrderBook.targetAmount` ของ quota book = โควตา; `quotaUsed` = การจองที่ยังไม่ถูกยกเลิก
  และคำสั่งซื้อไม่ถูกปฏิเสธ (ถูกปฏิเสธ = คืนโควตา)
- จองได้ตราบที่ `quotaRemaining >= minTicket` (`isBookingOpen`) — ยอดในฟอร์มจองถูกจำกัดที่
  โควตาคงเหลือ (`bookingRemaining`)
- ส่งคำสั่งซื้อทีละรายการจากคอลัมน์ "คำสั่งซื้อ" ในตารางการจองบนหน้า `/orders/:id`
  (ใช้ `submitOrder(productId, [bookingId])` ตัวเดิม)
- ปิดเมื่อใช้โควตาครบ → `useClosedProductIds` เอาออกจากลิสต์ใน catalogue; ปุ่มบนหน้าสินค้า
  เปลี่ยนเป็น "เต็มโควตา"
- Risk profile ที่ต้องการของหุ้นกู้ = Moderate (`requiredRiskProfile`)
- ปุ่มบนหน้าสินค้าใช้ `useQuotaBooking()` — หนึ่ง modal + toast ต่อหน้า toast สำเร็จมีปุ่ม
  "ดูรายการจอง" ไปที่ book

### แบบ transactions

ข้อมูลเป็น mock ทั้งหมดใน [`src/lib/transaction-mock-data.ts`](../src/lib/transaction-mock-data.ts)
(สร้างแบบ deterministic จากสินค้าใน catalogue + ลูกค้า mock) อ่านผ่าน
`useTransactions(asset)` — ต่อ backend แก้ที่ hook นั้นที่เดียว

กดที่แถวเปิด [`TransactionDetailModal`](<../src/app/(dashboard)/orders/TransactionDetailModal.tsx>)
— วางแบบใบเสร็จ: วงกลมสถานะ + หัวเรื่องว่าเกิดอะไรขึ้น แล้วเป็นแถว label ซ้าย/ค่าขวา
คั่นด้วยเส้นประ จบที่ยอดรวม อ่านอย่างเดียวทั้งหมด กดได้สองที่คือแถวลูกค้า (ไป `/client/:id`)
กับเลขที่รายการ (คัดลอก) label สี และรูปแบบตัวเลขใช้ร่วมกับตารางผ่าน
[`transaction-display.ts`](<../src/app/(dashboard)/orders/transaction-display.ts>)

## ลำดับงาน

```
Product Catalog → สินค้า (Global / Thai Structured)
   └─ "จองซื้อให้ลูกค้า"
        เลือกลูกค้า            ← list + ค้นหา บอกตั้งแต่ยังไม่เลือกว่าใครพร้อม
        └─ เลือกแล้ว → ฟอร์มเดียว (ไม่ใช่ wizard)
        Customer              ← ที่เลือกไว้ + ลิงก์ "เปลี่ยน"
        Account No            ← อ่านอย่างเดียว
        Wealth Status         ← Yes/No  · Open Wealth Declare
        Acknowledge Status    ← Yes/No  · Open Wealth Declare
        KYC Status            ← Yes/No
        Risk Profile Status   ← ระดับ / NOT FOUND · Risk Consent ⌄
        IC Name · IC Team     ← อ่านอย่างเดียว
        Notional Amount *     ← ขั้นต่ำ / ยอดที่ยังจองได้ / เงินสดคงเหลือของลูกค้า
        [Cancel] [จองซื้อ]     ← กดได้ต่อเมื่อครบ 4 ข้อ และจำนวนถูกต้อง

/orders/[productId]  ← ยอดจองรวมของสินค้านั้น จากลูกค้าหลายราย
   └─ ครบเป้าหมายแล้วเท่านั้น จึงกด "ส่งคำสั่งซื้อ" ได้
        └─ ส่งเป็นคำสั่งซื้อเดียว → ระบบหลังบ้าน → แจ้งเตือน "คำสั่งซื้อสำเร็จ"
```

**กฎที่ทั้งหน้าถูกสร้างรอบ ๆ มัน: ยอดไม่ครบ ส่งคำสั่งซื้อไม่ได้** — นี่คือเหตุผลที่เป้าหมาย
อยู่บนหัวหน้า ไม่ใช่ในแถวรายละเอียด และที่ปุ่มส่งตอนกดไม่ได้เขียนว่า "ยังขาด X" แทนที่จะ
เขียนชื่อปุ่มซ้ำ

### ขั้นของลูกค้าหนึ่งรายต่อสินค้าหนึ่งตัว

ชิปเหนือตารางในหน้า book คือ 4 ขั้นนี้ตามลำดับที่มันเกิดจริง
([`bookingPhase`](<../src/app/(dashboard)/orders/order-book.ts>)):

| ขั้น | หมายถึง | ข้อมูลที่อยู่เบื้องหลัง |
| --- | --- | --- |
| **Offer** | IC ส่งสินค้าไปให้ลูกค้า ยังไม่ตอบ | `ProductOffer` — ยังไม่มีรายการจอง ไม่มีจำนวนเงิน |
| **ตรวจสอบ** | ลูกค้าตอบรับ (หรือ IC จองให้) | `Booking` — เงินถูกเช็คตั้งแต่ตอนจองแล้ว |
| **รับคำสั่งซื้อสำเร็จ** | ระบบหลังบ้านรับคำสั่งซื้อแล้ว | submission `completed` |
| **ยกเลิก** | ลูกค้าปฏิเสธ Offer / ยกเลิกการจอง / คำสั่งซื้อถูกปฏิเสธ | offer `declined` หรือ booking `cancelled` |

**มีรายการจองเมื่อไหร่ = เลย Offer ไปแล้วเสมอ** — การจองคือคำตอบของ Offer ดังนั้น
Offer ที่ลูกค้าจองแล้วจะหายจากลิสต์ (แถวการจองพูดแทนได้ครบกว่า พร้อมจำนวนเงิน)
ดู `assembleOrderBook`

ส่ง Offer ได้จากปุ่ม "ส่ง Offer" เหนือตาราง — เลือกลูกค้าได้หลายรายพร้อมกัน
([`SendOfferModal`](<../src/app/(dashboard)/orders/SendOfferModal.tsx>)) ลูกค้าที่ยังขาด
เอกสารก็ส่งได้ (แถวบอกว่าขาดกี่รายการ) เพราะการถามว่าสนใจไหมไม่ต้องรอเอกสาร —
ด่านเอกสารอยู่ที่ฟอร์มจองซื้อ กดแถว Offer เปิด
[`OfferDetailModal`](<../src/app/(dashboard)/orders/OfferDetailModal.tsx>) ซึ่งมีปุ่มเดียว
คือบันทึกว่าลูกค้าปฏิเสธ

### ไม่มีขั้น "ตรวจสอบวงเงิน"

วงเงินถูกตัดสินตอนกรอกจำนวนในฟอร์มจอง — เกินเงินสดคงเหลือของลูกค้าเมื่อไหร่ ช่อง
Notional Amount ขึ้น error และปุ่ม "จองซื้อ" กดไม่ได้ (`amountCheck` ใน
[`OrderBookingModal.tsx`](<../src/app/(dashboard)/orders/OrderBookingModal.tsx>)) **ทุก
รายการจองที่มีอยู่จึงผ่านวงเงินแล้วเสมอ** ไม่มีอะไรหลังจากนั้นต้องถามอีก

ของเดิมเคยเป็น `Booking.credit` (`pending`/`sufficient`/`insufficient`) ที่ระบบหลังบ้าน
ตอบกลับมาหลังจอง ซึ่งทำให้มีสถานะหนังสือ `checking` ("รอตรวจสอบวงเงิน") และรายการ
จองเดียวที่วงเงินไม่พอค้างทั้งสินค้าไว้จนกว่า IC จะไปหาเจอแล้วยกเลิก — ตอนนี้ถูกลบออก
ทั้งหมด (type, สถานะ, ป้าย, ตัวนับ และ seed)

ผลพลอยได้: **Payment Status กับ Email Pre-Confirmation มีค่าตั้งแต่จองเสร็จ** — จองแล้ว
= "กันเงินแล้ว" และอีเมลยืนยันล่วงหน้า "ส่งแล้ว" (ดู `paymentStatus` / `emailStatus` ใน
[`booking-status.ts`](<../src/app/(dashboard)/orders/booking-status.ts>)) ไม่มี "ยังไม่…"
สำหรับรายการที่ยังอยู่อีกแล้ว

## การตรวจสอบความพร้อมลูกค้า

[`orders/order-requirements.ts`](<../src/app/(dashboard)/orders/order-requirements.ts>)

**4 ข้อ** ตามฟอร์มจริง มาจากสองที่ แต่ฟอร์มไม่แยกให้ IC เห็น

| ข้อ | ค่าที่แสดง | มาจาก | ส่งให้ลูกค้าทำเองได้? |
| --- | --- | --- | --- |
| Wealth Status | Yes / No / Pending / Expired | `order-requirements.json` | ✓ Wealth Declare |
| Acknowledge Status | Yes / No / Pending / Expired | `order-requirements.json` | ✓ Wealth Declare |
| KYC Status | Yes / Expired / NOT FOUND | `kycExpiry()` — ตัวเดียวกับหน้า Client 360 | **ไม่ได้** |
| Risk Profile Status | ระดับความเสี่ยง / NOT FOUND | `client.riskProfile` เทียบกับที่สินค้าต้องการ | ✓ Risk Consent |

Wealth กับ Acknowledge เป็นผลสองอย่างจากแบบแจ้งใบเดียว จึงไปที่เดียวกัน แต่
**ตกคนละข้อได้** (แจ้งความมั่งคั่งแล้วแต่ยังไม่รับทราบความเสี่ยงของผลิตภัณฑ์) จึงเป็นสองแถว

KYC ส่งให้ลูกค้าทำเองไม่ได้ (`selfService: false`) เพราะการทบทวน KYC เริ่มที่สาขากับตัว
ลูกค้า ไม่ใช่จากหน้าจองซื้อ — ใส่ไว้ในคำขอจะเป็นการขอสิ่งที่ลูกค้าไปทำเองไม่ได้

### ปุ่มเดียว ไม่ใช่ลิงก์รายข้อ

เดิมแต่ละการ์ดมีลิงก์สีน้ำเงินของตัวเอง ("Open Wealth Declare" / "Risk Consent ⌄")
ตอนนี้ยุบเป็น **ปุ่มเดียวใต้กริด** `ส่งให้ลูกค้าดำเนินการ (N รายการ)` ส่งทุกข้อที่ค้างไป
พร้อมกันครั้งเดียว

เหตุผล: ลิงก์แยกรายข้อเพราะแต่ละ record อยู่คนละระบบ แต่สิ่งที่ IC ทำเหมือนกันหมด คือ
ส่งลูกค้าไปทำให้ครบ — ระบบปลายทางเป็นรายละเอียดของการ route ไม่ใช่การตัดสินใจของคน
ที่กำลังคุยโทรศัพท์อยู่ และการเอาของที่คลิกได้ออกจากการ์ด คือสิ่งที่ทำให้ไอคอนใหญ่
ด้านขวาเป็นของชิ้นเดียวในการ์ด

ปุ่มหายไปเมื่อไม่มีอะไรให้ส่ง — ครบหมดแล้ว หรือเหลือแต่ `risk-profile` ที่ไม่มีฟอร์มไหน
แก้ได้ (กรณีหลังขึ้น Alert แดงแทน)

### สถานะของแต่ละข้อ

### เลือกลูกค้าเป็น list ไม่ใช่ dropdown

dropdown แสดงได้แค่ชื่อ — IC เลือกไปแล้วถึงรู้ว่าลูกค้าขาดเอกสาร 3 อย่าง
list มีที่พอจะตอบตั้งแต่ยังไม่เลือก ทุกแถวบอกผลตรวจของลูกค้าคนนั้นกับสินค้าตัวนี้เลย
("พร้อมจอง" / "ขาด N รายการ") เปลี่ยนคำถามจาก *เลือกลูกค้า* เป็น *เลือกลูกค้าที่ซื้อได้จริง*

ด้วยเหตุผลเดียวกัน คนที่พร้อมถูกเรียงขึ้นบน และหัวลิสต์สรุปว่า "จองได้เลย 2 จาก 8 ราย"
ตัวเลขนี้นับจาก**ผลค้นหา** ไม่ใช่ทั้ง book — ถ้านับทั้ง book มันจะเป็นตัวเลขของสิ่งที่คนอ่าน
มองไม่เห็น

พอเลือกแล้ว list หายไปทั้งหมด เหลือการ์ด Customer พร้อมลิงก์ **เปลี่ยน** เพื่อกลับมา

### รองรับลูกค้าเยอะ

ทดสอบด้วย 200 รายแล้ว modal ชน `max-h-[85vh]` และ scroll ข้างในตามปกติ สิ่งที่ต้องทำเพิ่ม
คือสองอย่างที่เห็นจากการทดสอบจริง:

- **หัวลิสต์ + ช่องค้นหาเป็น `sticky`** — ของเดิมเลื่อนหายไปพร้อมลิสต์ พอเลื่อนไปแถวที่ 150
  แล้วอยากค้นหา ต้องเลื่อนกลับขึ้นไปสุด ซึ่งเป็นสิ่งที่ลิสต์ยาว ๆ ทำให้อยากทำพอดี
- **รีเซ็ต scroll เมื่อผลค้นหาเปลี่ยน** — เบราว์เซอร์แค่ clamp ตำแหน่งเดิมให้พอดีลิสต์ใหม่
  ผลลัพธ์คือผลค้นหาเปิดมากลางลิสต์ และแถวแรกถูกบังอยู่ใต้หัวที่ sticky
  (รีเซ็ตตอน mount ด้วย ครอบคลุมกรณีกด "เปลี่ยน" กลับมา)

> ⚠️ **ยังไม่มี virtualization** — 200 ราย = ~2,200 DOM node ซึ่งยังไหว แต่ถ้าหลักพัน
> ควรให้ backend ทำ search/paginate แทนการส่งทั้ง book มา render ทีเดียว
> (ชั้นข้อมูลเป็น `Resource<T>` อยู่แล้ว เปลี่ยนที่ `useClients` จุดเดียว)

### ภาษาภาพของฟอร์ม

> **ขาว + มีขอบ = พิมพ์ได้** · **เทาทึบ = ระบบบอกคุณ**

ในฟอร์มมีช่องที่พิมพ์ได้แค่ 2 ช่อง คือ Customer (dropdown) กับ Notional Amount
ที่เหลือเป็น **การ์ดพื้นเทา** (`#f9fafb` + ขอบ `black/10` + `rounded-xl`) มี label อยู่ใน
การ์ด — เดิมทำเป็นกล่องสูงเท่า input ซึ่งชวนให้คลิกทั้งที่คลิกไม่ได้สักอัน

| สถานะ | บนการ์ด | ความหมาย | สิ่งที่ต้องทำ |
| --- | --- | --- | --- |
| `passed` | 🟢 ✓ เขียว | มีข้อมูลแล้ว | — |
| `pending` | 🟡 ⏱ เหลือง | ทำแล้ว รอตรวจ | **รอ** — ส่งซ้ำคือขอสิ่งที่ลูกค้าทำไปแล้ว |
| `expired` | 🟠 ⚠ ส้ม | เคยมี แต่หมดอายุ | ยื่นใหม่ |
| `missing` | 🔴 ✕ แดง | ยังไม่มีในระบบ | เปิดระบบที่เป็นเจ้าของ record |
| `failed` | 🔴 ✕ แดง | อ่านแล้วไม่ผ่านเกณฑ์ | ไม่มีอะไรที่ลูกค้าเซ็นแล้วแก้ได้ |

สีอยู่ที่ **ไอคอน + ตัวค่า** ไม่ได้ทำเป็น pill ซ้อนในการ์ด — การ์ดเป็นพื้นผิวอยู่แล้ว
ซ้อนอีกชั้นไม่ได้อะไรเพิ่ม

> ⚠️ ต้องใส่คลาสสีที่ **ตัวค่า** ด้วย ไม่ใช่ใส่ที่ parent แล้วให้สืบทอด — คลาส `type-*`
> ของ design system ตั้ง `color` ของตัวเอง สีจาก parent จะไปถึงไอคอน (inline SVG)
> แต่หยุดที่ตัวหนังสือ

`pending` / `expired` ไม่ใช่สีแดง เพราะคนละเรื่องกับ "ยังไม่มี" — `pending` อยู่ที่ผู้อนุมัติ
(ไล่ลูกค้าคือไล่ผิดคน) ส่วน `expired` เคยมีมาก่อน คนละบทสนทนากับไม่เคยมีเลย

ข้างค่ามีประโยคกำกับเสมอ — `detail` ถ้าแถวนั้นมีอะไรเจาะจง (วันหมดอายุ, ระดับที่ต้องการ)
ไม่งั้นใช้คำของสถานะนั้น เพราะค่าที่เขียนว่า "No" เฉย ๆ ไม่ได้บอกว่า "no อะไร"

เหนือกริดมีตัวนับ **"3 จาก 4"** — การ์ดตอบรายข้อ ตัวนับตอบทั้งกริด

Account No / IC Name / IC Team อยู่บนการ์ดเทาเหมือนกัน แต่ **ไม่มีไอคอนและไม่มีสี**
เพราะไม่มีสถานะให้รายงาน ถ้าใส่สีให้ด้วย สี่ข้อที่ต้องตัดสินจะเลิกเด่น

> ⚠️ **คลาส Tailwind ตัวใหม่จะไม่ขึ้นจนกว่าจะ restart `npm run dev`**
>
> Tailwind ที่นี่สแกน source อัตโนมัติ และ dev server ที่เปิดอยู่ก่อนที่โฟลเดอร์
> `orders/` จะถูกสร้าง **จะไม่สแกนโฟลเดอร์นี้ซ้ำ** — arbitrary class ที่มีอยู่เฉพาะในนี้
> จึงไม่ถูก generate เลย (`max-w-[840px]`, `text-[var(--fill-*-700)]`,
> `border-[var(--fill-red-600)]` ติดอยู่ใน DOM แต่ไม่มี CSS) ส่วน build production
> ไม่มีปัญหา
>
> เวลาเช็ค **ต้องวัด `getComputedStyle` ไม่ใช่ดูชื่อคลาส** — การเช็คว่าชื่อคลาสมีคำว่า
> `fill-red` ไหม ผ่านทุกเคสข้างบน ซึ่งเป็นสาเหตุที่หลุดไปสองรอบ

`failed` มีอยู่เพราะ Risk Profile: ระดับความเสี่ยง **มี** อยู่ในระบบ แค่ต่ำกว่าที่สินค้าต้องการ
ถ้าเรียกว่า `missing` ช่องจะขึ้น "NOT FOUND" ข้างค่าที่เพิ่งอ่านมาเทียบ ลูกค้าที่ติดแค่ข้อนี้
ลิงก์ Risk Consent จะกดไม่ได้ และขึ้น Alert แดงบอกตรง ๆ ว่าต้องประเมินความเสี่ยงใหม่

### ⚠️ Risk Consent ⌄ — ช่องทางส่งเป็นการเดา

caret เปิดเมนู 3 ช่องทาง (SMS / LINE / นัดที่สาขา) ใน `RISK_CONSENT_CHANNELS` —
ภาพ spec แสดงแค่ caret ไม่ได้ระบุรายการ **ต้องยืนยันรายการจริงก่อนส่งงาน**

### สิ่งที่ไม่ได้เก็บเป็นข้อมูล — เพราะคำนวณได้

- **Log** สร้างใหม่จากการจอง/คำสั่งซื้อ/คำขอ ทุกครั้งที่อ่าน (`buildLogs`) log ที่เขียนแยก
  คือ log ที่ขัดกับสิ่งที่มันบรรยายได้
- **เป้าหมายยอดจอง** อ่านจาก `requestNotionalSize` ของตัวสินค้าเอง ไม่ได้คัดลอกมาเก็บ

  > เงื่อนไขรายตัวมา ให้เปลี่ยนเป็นฟิลด์แล้วลบค่าคงที่ทิ้ง
- **ชื่อลูกค้า** join ที่ import time จาก `clients.json` เหมือน dataset อื่นทั้งหมด

### เรื่องรอบ (round)

การจองที่ถูกส่งไปแล้วจะไม่นับรวมเป้าหมายอีก — `openBookings` คือรอบที่เปิดอยู่ สินค้า
ตัวเดียวจึงเปิดรอบใหม่ได้เรื่อย ๆ โดยไม่เจอบาร์ที่เต็มอยู่แล้วจากคำสั่งซื้อที่จบไปนานแล้ว

หน้าหนังสือที่ส่งคำสั่งซื้อไปแล้วและยังไม่มีการจองใหม่ จะแสดงตัวเลขของ **รอบที่ส่งไป**
พร้อมบรรทัดบอกว่าเป็นรอบไหน (`headlineRound`) — ไม่งั้นจะได้ "0 USD · 0%" ใต้ป้าย
สีเขียว "คำสั่งซื้อสำเร็จ"
